# 知识入库队列与表结构说明

## 1. 设计目标

知识库模块使用 PostgreSQL 管理业务状态和任务队列，使用 Milvus 管理检索索引。第一版不引入 Redis、Celery、LightRAG、租户权限或分块增强任务。

设计重点：

1. 文件存储与知识索引分离。
2. 文档状态与某一次入库任务状态分离。
3. 多进程、多实例可以安全并发抢任务。
4. Worker 异常退出后任务可以自动恢复。
5. 每个分块可以追溯到知识库、文件、索引版本和原文。

## 2. 四张表

### 2.1 knowledge.knowledge_bases

保存知识库定义和默认索引配置。

核心字段：

- `knowledge_id`：对外稳定 ID。
- `collection_name`：Milvus Collection。
- `embedding_model`：知识库创建时绑定的 `model_configs.model_code`。
- `embedding_dimension`：从该模型的 `extra_config.dimension` 固化的 Collection 向量维度。
- `split_config`：知识库默认切片配置。
- `status`：`active / disabled / deleted`。

Embedding 维度决定 Collection Schema，创建后不能直接修改。更换维度应新建 Collection 并重建索引。

### 2.2 knowledge.knowledge_documents

保存知识库和 `agent.uploaded_files` 的关联及当前索引状态。Agent 与 Knowledge 位于同一个 `career_ai` 数据库，通过不同 Schema 隔离，因此 `file_id` 建立真实数据库外键。

核心字段：

- `knowledge_id + file_id`：唯一关系。
- `status`：`pending / indexing / indexed / failed / deleted`。
- `index_version`：当前成功索引版本。
- `chunk_count`：当前有效分块数量。
- `index_config`：最近一次真实生效的切片和 Embedding 配置快照。

文件名、路径、MIME、大小等继续由文件服务维护，不在知识库表重复保存。

### 2.3 knowledge.ingestion_runs

既是任务队列，也是每次入库运行记录。

核心字段：

- `run_id`：任务主键。
- `operation`：`ingest / reindex / delete`。
- `status`：`pending / running / completed / failed / cancelled`。
- `priority`、`available_at`：优先级和退避重试时间。
- `worker_id`、`heartbeat_at`：任务所有权和活性。
- `retry_count`、`max_retries`：自动重试控制。
- `started_at`、`completed_at`：运行耗时和审计。

部分唯一索引保证同一文档、同一操作最多只有一个活跃任务：

```sql
UNIQUE (document_id)
WHERE status IN ('pending', 'running')
```

### 2.4 knowledge.knowledge_chunks

保存分块证据和 Milvus 映射。

核心字段：

- `chunk_id`：稳定、可重算且不超过 Milvus 长度限制。
- `index_version`、`chunk_index`：版本与文档内顺序。
- `raw_content`、`content_hash`：原始证据和完整性检查。
- `context`、`metadata`：标题路径等结构化上下文。
- `vector_id`：Milvus 主键。

## 3. PostgreSQL 抢任务

Worker 通过一条事务 SQL 原子选择并更新任务：

```sql
WITH candidate AS (
    SELECT run_id
    FROM knowledge.ingestion_runs
    WHERE status = 'pending' AND available_at <= NOW()
    ORDER BY priority DESC, created_at ASC
    FOR UPDATE SKIP LOCKED
    LIMIT 1
)
UPDATE knowledge.ingestion_runs AS run
SET status = 'running',
    worker_id = :worker_id,
    heartbeat_at = NOW()
FROM candidate
WHERE run.run_id = candidate.run_id
RETURNING run.*;
```

`SKIP LOCKED` 的作用：

- Worker A 锁住任务 1 后，Worker B 不等待任务 1，而是继续寻找任务 2。
- 多个 FastAPI 实例可以共用同一张任务表。
- 数据库事务决定唯一所有者，不依赖进程内锁。

## 4. 心跳与故障恢复

执行任务期间，Worker 定期更新 `heartbeat_at`。

当运行中任务超过 `KNOWLEDGE_INGESTION_STALE_SECONDS` 没有心跳：

1. 增加 `retry_count`。
2. 未超过 `max_retries`：改回 `pending`，设置新的 `available_at`。
3. 超过次数：改为 `failed`，文档也改为 `failed`。
4. 原任务记录不删除，便于排查。

服务正常关闭时不会把执行中的任务误判为成功；下次启动后由心跳超时机制恢复。

## 5. 一致性边界

PostgreSQL 和 Milvus 不支持同一个数据库事务，因此执行器采用可重试补偿：

1. 重试或重建前按 `file_id` 清理旧向量。
2. 逐块生成向量并写入 Milvus。
3. 全部向量成功后，替换 PostgreSQL 分块证据。
4. 最后把任务标记为 `completed`，文档标记为 `indexed`。
5. 中途失败时任务重排；下一次执行先清理上次部分写入。

这属于最终一致性，不宣称跨 PostgreSQL/Milvus 强事务。

## 6. 启动配置

Worker 是知识入库基础组件，会随 AI-backend 自动启动，不提供关闭开关。部署前必须完成建表并准备好 Milvus 和知识库绑定的 Embedding 模型。以下配置用于调整 Worker 并发、轮询、心跳与重试策略：

```env
KNOWLEDGE_INGESTION_WORKER_COUNT=1
KNOWLEDGE_INGESTION_POLL_INTERVAL_SECONDS=1
KNOWLEDGE_INGESTION_HEARTBEAT_SECONDS=10
KNOWLEDGE_INGESTION_STALE_SECONDS=60
KNOWLEDGE_INGESTION_RECOVERY_INTERVAL_SECONDS=30
KNOWLEDGE_INGESTION_MAX_RETRIES=3
KNOWLEDGE_INGESTION_RETRY_DELAY_SECONDS=5
```

启用时，服务启动阶段会检查四张表。缺表会直接阻止启动并提示需要执行的 SQL。

## 7. 当前限制

- 当前 Worker 实现了 `ingest` 和 `reindex`；`delete` 预留在状态模型中，执行器尚未启用。
- Embedding 和 Milvus 均按模型 `extra_config.batch_size` 分批处理，默认每批 32 条；批量响应按照 `index` 恢复输入顺序并校验数量和向量维度。
- 正式检索接口仍需把 `kb_ids` 映射为 Collection。
