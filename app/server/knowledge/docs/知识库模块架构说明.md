# 知识库模块架构说明

## 模块定位

Knowledge 与 Agent、File 一样，是 AI-backend 内的基础能力模块。它拥有独立 API 和业务边界，但与 AI-backend 使用同一进程、同一套配置、日志、生命周期和依赖文件。

```text
AI-backend
  ├─ Agent
  ├─ File
  └─ Knowledge
       ├─ Split
       ├─ Embedding
       ├─ Vector Store
       ├─ Retrieval
       └─ Ingestion
```

Split、Embedding 和 Retrieval 是 Knowledge 的内部组件，不通过 HTTP 相互调用。只有未来出现明确的独立扩缩容需求时，才考虑在不改变 Service 接口的前提下拆成独立服务。

## 分层职责

### API

只负责请求校验、调用 Service 和返回全局 `Result`，不直接操作 Milvus 或模型服务。

### KnowledgeService

作为统一能力门面，负责向 API 和 Agent 层隐藏底层模块组织方式。

### IngestionService

后续负责完整入库编排：

```text
读取 File 服务 content.md
  -> Split
  -> 补充 kb_id、file_id、chunk_id 和来源信息
  -> Embedding
  -> Milvus 写入
  -> PostgreSQL 更新索引状态
```

### Retrieval

负责向量、关键词、混合、全文召回和 Rerank。当前底层输入为 Collection；正式业务入口将由 KnowledgeService 把 `kb_ids` 映射为 Collection。

### PostgreSQL 与 Milvus

- PostgreSQL 是事实数据源，保存知识库、文档关系、索引任务和配置快照。
- Milvus 只保存 Chunk 正文、向量和检索所需元数据。
- 删除、重建和失败恢复必须由 IngestionService 保证两边状态最终一致。

## 设计约束

1. Knowledge 不重复实现文件上传与文档转 Markdown，统一复用 File 服务。
2. API 不允许直接编排 Split、Embedding 和 Milvus 写入。
3. Embedding 不自行创建 PostgreSQL 表。
4. Agent 不直接提供 Collection 名称；运行时只允许注入经过上游授权的 `kb_ids`。
5. 入库接口必须幂等，同一个文件重复提交不能产生重复 Chunk。
