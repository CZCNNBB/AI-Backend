# 业务平台接入与会话隔离改造方案

## 1. 文档目的

本文用于沉淀 AI-backend 接入多个外部业务平台时的第一阶段改造方向，统一以下问题的处理方式：

- AI-backend 如何识别当前请求来自哪个业务平台。
- Agent 和 MCP Tool 如何与一个或多个业务平台建立归属关系。
- 业务平台用户的会话、消息、运行记录和 Checkpoint 如何隔离。
- 业务平台用户 Token 如何安全透传给外部业务 API。
- Agent 配置阶段和运行阶段分别承担哪些校验职责。

当前项目处于开发阶段，本次改造不考虑旧数据兼容。允许清空相关测试数据并直接调整表结构、接口参数和代码模型，不增加旧字段兼容、默认租户或双写逻辑。

## 2. 第一阶段目标

第一阶段只实现平台身份、资源归属、会话隔离和业务 Token 透传，不在 AI-backend 内重复建设业务系统自己的角色权限体系。

```text
业务平台后端
  → 使用 AI-backend 签发的平台 API Key 调用 /agent/messages
  → AI-backend 根据 API Key 确定 platform_id
  → 业务平台传入 external_user_id 和业务用户 Token
  → AI-backend 校验当前平台是否绑定了目标 Agent
  → Agent 按已经保存的配置直接组装 MCP Tool
  → FastMCP 将业务用户 Token 注入目标 API 的 Authorization 请求头
  → 目标业务 API 判断当前用户是否有具体业务权限
```

第一阶段明确不实现：

- AI-backend 内部的业务角色、菜单权限和数据权限。
- 用户与 MCP Tool 的细粒度授权关系。
- Agent 组装时再次按平台动态过滤 MCP Tool。
- 平台级知识库隔离、调用额度、限流和计费。
- 业务用户 Token 持久化、续期和后台长期凭证托管。
- 浏览器直接持有平台 API Key 的调用方式。

## 3. 核心身份模型

### 3.1 两类凭证必须分离

| 凭证 | 签发方 | 作用 | 是否持久化 |
| --- | --- | --- | --- |
| 平台 API Key | AI-backend | 识别并认证业务平台 | 内网阶段保存明文、哈希和前缀 |
| 业务用户 Token | 外部业务平台 | 调用目标业务 API 时执行用户权限校验 | 不保存，仅本次运行使用 |

建议的调用请求头：

```http
X-API-Key: aik_xxxxxxxxx
X-Business-Authorization: Bearer business-user-token
```

`platform_id` 必须通过 `X-API-Key` 在服务端解析得到，不能信任请求体传入的 `platform_id`。

### 3.2 用户身份使用 external_user_id

AI-backend 第一阶段不建立完整的内部用户体系，也不复制业务平台用户表。业务方只需要传入其系统中稳定的用户标识：

```json
{
  "external_user_id": "user_10086"
}
```

不同业务平台可能拥有相同的用户 ID，因此真正的用户隔离键为：

```text
(platform_id, external_user_id)
```

字段使用 `external_user_id`，而不是含义模糊的 `user_id`，为后续增加 AI-backend 内部用户主键预留空间。

## 4. 资源归属关系

### 4.1 Agent 与业务平台是多对多关系

一个 Agent 可以提供给多个业务平台，一个业务平台也可以使用多个 Agent：

```text
business_platforms >──< agent_templates
```

### 4.2 MCP Tool 与业务平台是多对多关系

一个 MCP Tool 可以提供给多个业务平台，一个业务平台也可以绑定多个 MCP Tool：

```text
business_platforms >──< mcp_tools
```

因此，不在 `agent.agent_templates` 或 `mcp.mcp_tools` 中增加单值 `platform_id`，统一通过关联表表达归属关系。

### 4.3 Agent 配置阶段校验工具范围

当前 Agent 使用的 MCP Tool 名称继续保存在 `agent.agent_templates.config` JSONB 的 `tools` 字段中，不恢复旧的 `agent_mcp_tools` 表，避免出现两个工具配置数据源。

为了保证运行阶段不需要再次按平台过滤，保存 Agent 配置时必须满足：

```text
Agent 绑定的平台集合 ⊆ 每一个已选 MCP Tool 绑定的平台集合
```

示例：

| Agent 绑定平台 | Tool 绑定平台 | 是否允许挂载 |
| --- | --- | --- |
| 平台 A | 平台 A | 允许 |
| 平台 A | 平台 A、B | 允许 |
| 平台 A、B | 平台 A、B | 允许 |
| 平台 A、B | 平台 A | 不允许 |
| 平台 A、B | 平台 B | 不允许 |

前端在配置 Agent 时只展示满足条件的 MCP Tool，后端保存时必须执行同样的校验，不能只依赖前端过滤。

修改 Agent 平台绑定或者删除 MCP Tool 平台绑定时，也必须重新校验现有 Agent 配置。第一阶段直接阻止会造成配置失效的修改，并返回明确提示，不做自动解绑。

### 4.4 运行阶段的校验边界

业务平台调用 Agent 时只执行一次入口归属校验：

```text
当前 API Key 对应的 platform_id 是否绑定了请求中的 agent_id
```

校验通过后，Agent 直接按照模板 `config.tools` 组装 MCP Tool，不在组装过程中重复执行平台过滤。

Plan、A2A、附件读取、知识库检索等代码内置能力不属于外部 MCP Tool，继续由 Agent 功能开关控制，不参与平台与 MCP Tool 的关联关系。

## 5. 数据库目标结构

### 5.1 新增 platform 模式

PostgreSQL 新增独立的 `platform` schema：

```text
ai
├── agent
├── knowledge
├── mcp
└── platform
    ├── business_platforms
    ├── business_platform_api_keys
    ├── business_platform_agents
    └── business_platform_mcp_tools
```

### 5.2 业务平台表

```sql
CREATE SCHEMA IF NOT EXISTS platform;

CREATE TABLE platform.business_platforms (
    id BIGSERIAL PRIMARY KEY,
    platform_code VARCHAR(100) NOT NULL UNIQUE,
    platform_name VARCHAR(200) NOT NULL,
    description TEXT,
    status VARCHAR(30) NOT NULL DEFAULT 'enabled',
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    CONSTRAINT ck_business_platforms_status
        CHECK (status IN ('enabled', 'disabled'))
);
```

### 5.3 平台 API Key 表

API Key 独立成表，便于后续轮换、禁用和一个平台签发多个 Key。当前为公司内网阶段，数据库保存完整明文供管理调试自动回填，同时保留不可逆哈希用于请求鉴权。

```sql
CREATE TABLE platform.business_platform_api_keys (
    id BIGSERIAL PRIMARY KEY,
    platform_id BIGINT NOT NULL,
    key_name VARCHAR(100) NOT NULL DEFAULT 'default',
    key_prefix VARCHAR(30) NOT NULL,
    api_key VARCHAR(255) NOT NULL,
    key_hash VARCHAR(64) NOT NULL UNIQUE,
    status VARCHAR(30) NOT NULL DEFAULT 'enabled',
    expires_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    CONSTRAINT fk_platform_api_keys_platform
        FOREIGN KEY (platform_id)
        REFERENCES platform.business_platforms(id)
        ON DELETE CASCADE,

    CONSTRAINT ck_platform_api_keys_status
        CHECK (status IN ('enabled', 'disabled'))
);

CREATE INDEX idx_platform_api_keys_platform_id
    ON platform.business_platform_api_keys(platform_id);
```

平台 API Key 使用高强度随机值生成。数据库明文只允许内网管理接口按 Agent 和平台读取，业务请求仍通过 Hash 查询认证；任何日志都不能记录完整 Key。未来对公网部署时，应改为密文存储或恢复为只保存 Hash。

### 5.4 平台与 Agent 关联表

关联表使用 `agent.agent_templates.id` 作为外键，外部接口仍然使用稳定的 `agent_id`。

```sql
CREATE TABLE platform.business_platform_agents (
    platform_id BIGINT NOT NULL,
    agent_template_id BIGINT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    PRIMARY KEY (platform_id, agent_template_id),

    CONSTRAINT fk_platform_agents_platform
        FOREIGN KEY (platform_id)
        REFERENCES platform.business_platforms(id)
        ON DELETE CASCADE,

    CONSTRAINT fk_platform_agents_agent
        FOREIGN KEY (agent_template_id)
        REFERENCES agent.agent_templates(id)
        ON DELETE CASCADE
);

CREATE INDEX idx_platform_agents_agent_id
    ON platform.business_platform_agents(agent_template_id);
```

### 5.5 平台与 MCP Tool 关联表

关联表使用 `mcp.mcp_tools.id` 作为外键，Agent 模板中的 `config.tools` 仍保存 MCP Tool 的稳定唯一名称 `name`。

```sql
CREATE TABLE platform.business_platform_mcp_tools (
    platform_id BIGINT NOT NULL,
    mcp_tool_id BIGINT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    PRIMARY KEY (platform_id, mcp_tool_id),

    CONSTRAINT fk_platform_mcp_tools_platform
        FOREIGN KEY (platform_id)
        REFERENCES platform.business_platforms(id)
        ON DELETE CASCADE,

    CONSTRAINT fk_platform_mcp_tools_tool
        FOREIGN KEY (mcp_tool_id)
        REFERENCES mcp.mcp_tools(id)
        ON DELETE CASCADE
);

CREATE INDEX idx_platform_mcp_tools_tool_id
    ON platform.business_platform_mcp_tools(mcp_tool_id);
```

### 5.6 调整 Agent 会话表

`agent.agent_conversations` 必须直接记录平台和外部用户归属：

```sql
ALTER TABLE agent.agent_conversations
ADD COLUMN platform_id BIGINT NOT NULL,
ADD COLUMN external_user_id VARCHAR(150) NOT NULL;

ALTER TABLE agent.agent_conversations
ADD CONSTRAINT fk_agent_conversations_platform
FOREIGN KEY (platform_id)
REFERENCES platform.business_platforms(id);

CREATE INDEX idx_agent_conversations_platform_user
ON agent.agent_conversations(platform_id, external_user_id, updated_at DESC);

CREATE INDEX idx_agent_conversations_owner
ON agent.agent_conversations(platform_id, external_user_id, conversation_id);
```

由于本次不兼容旧数据，应先清空会话、消息和运行记录，再直接添加 `NOT NULL` 字段，不采用“先允许为空、后续补数据”的过渡方案。

`conversation_id` 继续使用全局唯一且难以猜测的 ID，并保留当前唯一约束。数据访问时仍然必须带上完整归属条件：

```sql
WHERE platform_id = :platform_id
  AND external_user_id = :external_user_id
  AND conversation_id = :conversation_id
```

### 5.7 调整 Agent 运行记录表

`agent.agent_runs` 同步保存平台和外部用户，便于运行监控、审计、统计和故障排查：

```sql
ALTER TABLE agent.agent_runs
ADD COLUMN platform_id BIGINT NOT NULL,
ADD COLUMN external_user_id VARCHAR(150) NOT NULL;

ALTER TABLE agent.agent_runs
ADD CONSTRAINT fk_agent_runs_platform
FOREIGN KEY (platform_id)
REFERENCES platform.business_platforms(id);

CREATE INDEX idx_agent_runs_platform_user
ON agent.agent_runs(platform_id, external_user_id, started_at DESC);
```

主 Agent 和 A2A 子 Agent 必须继承相同的 `platform_id` 与 `external_user_id`。

### 5.8 Agent 消息表暂不重复保存归属字段

`agent.agent_messages` 已通过 `conversation_id` 关联 `agent.agent_conversations`，第一阶段不重复增加 `platform_id` 和 `external_user_id`。

读取、删除消息时必须先通过完整归属条件获取会话，再操作该会话下的消息，禁止仅凭 `conversation_id` 或 `message_id` 越过会话归属检查。

### 5.9 MCP Tool 业务 Token 目标请求头

MCP Tool 不再预设 Bearer、Basic、API Key 等认证类型，也不再使用 `auth_type` 和
`auth_config`。每个 Tool 只保存一个可选的 `business_token_header`：

- 为空：不透传本次业务用户凭证。
- 填写 `X-Token`：原样发送 `X-Token: <业务用户凭证>`。
- 填写 `Authorization`：原样发送 `Authorization: <业务用户凭证>`。

完整规则以 `docs/AI平台调用业务平台API权限校验方案.md` 为准。

## 6. 会话隔离方案

### 6.1 AI-backend 维护用户与会话关系

业务平台不需要自行维护完整的“用户—conversation_id”关系。AI-backend 根据 `platform_id + external_user_id` 管理和查询会话：

```text
platform_id
└── external_user_id
    └── conversation_id
        ├── messages
        ├── runs
        └── checkpoints
```

业务方可以为了页面状态缓存最近使用的 `conversation_id`，但这不是接入 AI-backend 的必要条件。

### 6.2 conversation_id 由 AI-backend 生成

首次发送消息时允许 `conversation_id` 为空：

```json
{
  "agent_id": "order-agent",
  "external_user_id": "user_10086",
  "conversation_id": "",
  "message": "查询最近的订单"
}
```

AI-backend 创建会话并在普通响应或 SSE 元事件中返回新生成的 `conversation_id`。后续消息继续携带该值。

### 6.3 Checkpoint 使用内部命名空间

LangGraph Checkpointer 不直接使用业务方可控的简单用户 ID。内部 `thread_id` 按以下结构构造：

```text
platform:{platform_id}:user:{external_user_id}:conversation:{conversation_id}
```

该值只在 AI-backend 内部使用，不作为外部 API 的会话标识。A2A 子 Agent 继承主运行的同一个命名空间。

## 7. 业务用户 Token 透传

### 7.1 Token 进入独立运行时凭证上下文

业务用户 Token 不能放入普通 `inputs`、Tool 参数或模型上下文。建议建立独立的运行时凭证对象：

```python
runtime_credentials = {
    "business_token": "business-user-token",
}
```

该对象沿调用链传递：

```text
/agent/messages
  → Agent Runtime Context
  → Agent MCP Adapter
  → FastMCP HTTP 执行器
  → Tool.business_token_header 指定的目标请求头
```

### 7.2 Token 安全边界

业务用户 Token 禁止写入：

- Agent 会话和消息。
- Agent 运行记录。
- LangGraph Checkpoint。
- MCP Tool 输入 Schema 和调用参数。
- MCP Tool 数据库配置。
- 普通日志、异常日志和 SSE 事件。

配置了 `business_token_header` 的工具在缺少运行时 Token 时返回结构化错误：

```json
{
  "code": "BUSINESS_CREDENTIAL_MISSING",
  "message": "当前操作需要业务用户凭证，请重新登录或重新发起请求"
}
```

目标 API 返回结果建议统一转换：

- `401`：业务 Token 无效或已过期。
- `403`：当前业务用户没有权限。
- 网络错误、超时和 `5xx`：业务接口异常，不能解释为没有权限。

## 8. API 与模块改造方向

### 8.1 新增 platform 模块

建议新增：

```text
app/server/platform
├── api
├── src/models.py
├── src/schemas.py
├── src/repository.py
├── src/service.py
└── tests
```

第一阶段管理能力包括：

- 创建、编辑、启用和停用业务平台。
- 为业务平台签发、查看前缀和停用 API Key。
- 配置业务平台与 Agent 的多对多关系。
- 配置业务平台与 MCP Tool 的多对多关系。
- 查询指定 Agent 当前可选择的 MCP Tool。

### 8.2 新增平台认证依赖

平台调用接口通过统一 FastAPI 依赖解析 `X-API-Key`：

```text
读取 X-API-Key
  → 计算哈希
  → 查询有效 API Key
  → 检查业务平台状态
  → 构造 PlatformPrincipal
```

建议的请求身份对象：

```python
PlatformPrincipal(
    platform_id=1,
    platform_code="order_system",
)
```

管理端接口与业务调用接口应区分。第一阶段平台 API Key 只用于 `/agent/messages`、会话历史和运行查询等业务调用接口，不直接替代未来的 AI-backend 管理员认证。

### 8.3 调整 Agent 消息请求

`/agent/messages` 请求增加必填的 `external_user_id`。`platform_id` 不出现在请求模型中：

```json
{
  "agent_id": "order-agent",
  "external_user_id": "user_10086",
  "conversation_id": "",
  "message": "查询我的订单",
  "stream": true
}
```

业务用户 Token 从 `X-Business-Authorization` 读取，不放入 JSON 请求体。

### 8.4 调整会话接口

会话列表、详情、消息列表和删除接口统一从认证依赖取得 `platform_id`，从请求取得 `external_user_id`，Repository 查询强制携带二者。

业务方不需要维护本地会话映射，可以通过 `platform_id + external_user_id` 查询 AI-backend 中的会话列表。

### 8.5 调整 Agent 配置接口

Agent 创建或编辑流程调整为：

```text
选择一个或多个业务平台
  → 后端查询同时覆盖这些平台的 MCP Tool
  → 前端展示可选工具
  → 保存 Agent 配置
  → 后端再次校验平台集合和工具集合
  → 同一事务保存 Agent、平台绑定和 config.tools
```

## 9. 前端改造方向

### 9.1 业务平台管理

新增业务平台管理页面，第一阶段支持：

- 平台列表和状态。
- 新增、编辑业务平台。
- 生成 API Key，并允许内网 Agent 调试页按关联平台自动回填。
- 停用或者重新签发 API Key。
- 查看平台绑定的 Agent 和 MCP Tool。

### 9.2 Agent 配置页面

Agent 配置页面新增“所属业务平台”多选框。必须先选择业务平台，再加载可选 MCP Tool。

修改业务平台选择后，如果已有工具不再满足全部平台覆盖条件，前端应明确标记冲突并禁止保存，不静默删除用户已经选择的工具。

### 9.3 MCP Tool 配置页面

MCP Tool 新建和编辑页面新增“所属业务平台”多选框和可选的“业务 Token 目标请求头”。
所有 Tool 第一阶段都必须至少绑定一个业务平台。

## 10. 调用拓扑约束

第一阶段推荐的部署调用方式：

```text
业务平台前端
  → 业务平台后端
  → AI-backend
```

正式业务接入时，平台 API Key 必须保存在业务平台后端，不能放入业务浏览器、移动端安装包或公开前端配置中。AI-backend 内网管理页面为了联调可以临时读取明文 Key；业务平台后端仍负责根据自己的登录态提供可信的 `external_user_id` 和业务用户 Token。

如果未来需要浏览器直接调用 AI-backend，必须增加业务 JWT 验签、签名身份凭证或者 Token Introspection，不能继续使用可被所有浏览器用户读取的平台 API Key。

## 11. 开发阶段数据处理原则

本次改造明确不兼容旧数据，实施时遵循以下原则：

- 清空现有 Agent 会话、消息、运行记录和 Checkpoint 测试数据。
- 直接给会话与运行表增加 `NOT NULL` 的平台和外部用户字段。
- 不保留没有 `external_user_id` 的旧请求格式。
- 不增加默认 `platform_id`、匿名平台或者旧接口降级逻辑。
- SQLModel、Repository、Service、API 和前端在同一次改造中同步更新。
- 重新创建测试业务平台、API Key、Agent 绑定和 MCP Tool 绑定数据。

数据清理存在破坏性，实际实施时应先停止应用，并由开发者确认需要清空的具体表后再执行。

## 12. 推荐实施顺序

### 阶段一：数据库与 platform 模块

1. 清空现有会话、消息、运行和 Checkpoint 测试数据。
2. 创建 `platform` schema 和四张平台表。
3. 调整 `agent_conversations`、`agent_runs` 和 `mcp_tools`。
4. 新增对应 SQLModel、Repository、Service 和管理 API。
5. 实现 API Key 生成、内网明文保存、哈希认证和短事务认证依赖。

### 阶段二：Agent 与 MCP Tool 配置

1. Agent 创建和编辑接口支持业务平台多选。
2. MCP Tool 创建和编辑接口支持业务平台多选。
3. 实现“Agent 平台集合必须被 Tool 平台集合完全覆盖”的查询与保存校验。
4. 实现平台绑定变更时的关联配置保护。
5. 更新 Agent 和 MCP Tool 管理前端。

### 阶段三：会话隔离

1. `/agent/messages` 增加平台认证和 `external_user_id`。
2. 会话创建、读取、更新和删除统一使用完整归属条件。
3. 运行记录写入 `platform_id` 和 `external_user_id`。
4. A2A 子 Agent 继承平台和用户身份。
5. Checkpointer 使用带平台与用户命名空间的内部 `thread_id`。

### 阶段四：业务 Token 透传

1. 请求头读取 `X-Business-Authorization`。
2. 新增独立 `runtime_credentials` 上下文。
3. MCP Tool 增加可选的 `business_token_header`。
4. FastMCP 执行器把业务凭证原样注入配置的目标请求头。
5. 统一处理缺少凭证、`401`、`403`、超时和业务接口异常。
6. 检查日志、Checkpoint、消息和 SSE，确认不存在 Token 泄漏。

## 13. 验收标准

本次改造完成后必须满足：

- 无有效平台 API Key 时不能调用受保护的 Agent 接口。
- API Key 能唯一解析到一个启用状态的业务平台。
- 一个 Agent 和一个 MCP Tool 都可以绑定多个业务平台。
- Agent 配置页面只展示满足全部平台覆盖条件的 MCP Tool。
- 后端能够拒绝绕过前端提交的不合法 Agent 工具配置。
- 未绑定目标 Agent 的业务平台不能调用该 Agent。
- 相同 `external_user_id` 在不同平台下拥有完全独立的会话。
- 同一平台下不同 `external_user_id` 不能互相读取会话和消息。
- 会话、运行记录和 Checkpoint 均包含正确的平台与用户隔离维度。
- 配置了 `business_token_header` 的工具能够使用本次业务 Token 调用目标 API。
- 业务 Token 不出现在数据库、Checkpoint、日志、Tool Schema 和 SSE 中。
- 业务 API 返回 `401`、`403` 和系统异常时，Agent 能获得明确且不泄露敏感信息的结构化结果。

## 14. 后续演进方向

业务平台数量和安全要求提高后，可以在当前结构上继续增加：

- 平台与知识库的多对多绑定。
- 平台级 Agent、Tool、模型和知识库调用限额。
- 平台级并发控制、限流和计费。
- API Key 轮换、使用记录和最后访问时间。
- 平台用户表、长期记忆和用户偏好。
- 浏览器直连场景下的业务 JWT 验签。
- 后台任务所需的短期凭证交换和安全凭证托管。
- 更细粒度的平台、角色、Agent 和 Tool 授权策略。

这些增强项不改变第一阶段确定的核心关系：平台 API Key 识别业务平台，`external_user_id` 隔离业务用户，Agent 与 MCP Tool 通过多对多关系归属业务平台，具体业务操作权限继续由目标业务 API 校验。
