# 接入会话上下文总结中间件方案

## 1. 背景与目标

当前平台使用 LangGraph Checkpointer 保存 Agent 的会话工作记忆。随着同一 `conversation_id` 的持续对话，Checkpointer 中的 `messages` 会不断增长，带来三个问题：

1. 模型输入 Token 持续增加，调用成本和响应耗时上升。
2. 长上下文会降低模型对当前任务的关注度。
3. 达到模型上下文窗口后，运行可能失败或被动截断。

本方案引入会话上下文总结中间件：在模型调用前检测历史消息规模，必要时将早期消息压缩为摘要，同时保留近期消息和完整的工具调用配对关系。

核心目标：

- Agent 保持长期对话的连续性。
- 控制 Checkpointer 中的工作上下文长度。
- 不影响用户可见的完整会话历史。
- 总结过程不向前端 SSE 冒泡为普通 Agent 回复。
- 总结失败不影响主 Agent 本次运行。

## 2. 现有架构与边界

平台已有两套不同用途的数据：

| 数据位置 | 用途 | 是否允许压缩 |
| --- | --- | --- |
| `agent.agent_messages` | 用户可见会话历史，保存用户问题与最终回复 | 否 |
| LangGraph Checkpointer | Agent 的工作记忆、工具消息和运行状态 | 是 |

总结中间件只处理 Checkpointer 的 `messages` 状态，不修改 `agent_messages`。

因此，压缩后：

```text
用户界面：仍可读取完整历史问答
Agent 工作记忆：历史摘要 + 最近消息
```

Checkpointer 不能作为永久会话档案。即使 PostgreSQL Checkpointer 可能保留旧 checkpoint 快照，也不应依赖旧快照实现用户会话历史查询。

## 3. 当前 LangChain 版本行为

当前 conda 环境使用 `langchain==1.3.11`。官方 `SummarizationMiddleware` 的行为是：

1. 在 `before_model` / `abefore_model` 中统计 `messages` Token。
2. 超过 `trigger` 阈值后，划分早期消息和近期保留消息。
3. 调用指定模型生成摘要。
4. 使用 `RemoveMessage(id=REMOVE_ALL_MESSAGES)` 清理当前状态中的历史消息。
5. 写回一条摘要 `HumanMessage` 和近期保留消息。

官方摘要消息带有：

```python
additional_kwargs={"lc_source": "summarization"}
```

官方实现不使用单独的 `summary_text` State 字段。摘要本身作为 `messages` 中的一条内部消息参与下一次总结，因此新的摘要能够覆盖此前摘要与新增早期消息。

## 4. 总体方案

新增 `ConversationSummarizationMiddleware`，继承 LangChain 官方 `SummarizationMiddleware`。仅在模板配置 `context_summarization` 且本次存在 `conversation_id` 时装配：

```text
ConversationSummarizationMiddleware
    └── SummarizationMiddleware
```

不从零实现消息切割、工具消息配对和 Token 计算逻辑；优先复用官方能力，仅针对平台需求扩展：

- 总结模型流式隔离。
- 总结失败时保持原状态。
- 平台中文总结 Prompt。
- 日志和可观测性。

第一版不在 API 请求参数或 `optional_features` 中暴露会话总结开关。是否启用完全由 Agent 模板的 `context_summarization` 对象决定：对象不存在或为 `null` 时不装配中间件；对象存在时才启用。

模板示例：

```json
{
  "runtime_options": {
    "model_code": "chat-main"
  },
  "context_summarization": {
    "model_code": "chat-summary",
    "trigger_tokens": 12000,
    "keep_messages": 20,
    "trim_tokens_to_summarize": 4000
  }
}
```

`context_summarization.model_code` 是独立总结模型，必须指向已启用的 `chat` 模型。它不复用主 Agent 的 `runtime_options.model_code`。

## 5. 运行流程

```text
Agent 准备调用模型
    ↓
ConversationSummarizationMiddleware.abefore_model
    ↓
统计 Checkpointer 当前 messages 的 Token
    ↓
未达到阈值 -> 不处理，继续调用主模型
    ↓
达到阈值 -> 划分早期消息与近期消息
    ↓
保护 SystemMessage、AIMessage/ToolMessage 配对消息
    ↓
调用带 nostream 标记的总结模型
    ↓
成功 -> 当前 state.messages = [摘要消息 + 近期消息]
失败 -> 返回 None，保留原 state.messages
    ↓
主 Agent 继续执行
```

## 6. Token 策略

采用 Token 阈值触发，不按消息条数触发。以下参数直接由模板 `context_summarization` 配置：

```python
trigger = ("tokens", trigger_tokens)
keep = ("messages", keep_messages)
trim_tokens_to_summarize = trim_tokens_to_summarize
```

说明：

- `trigger_tokens`：当前工作消息达到阈值后尝试压缩。
- `keep_messages`：保留近期消息数量，由官方逻辑确保工具调用配对不被拆开。
- `trim_tokens_to_summarize`：如果待总结内容本身过大，限制发送给总结模型的 Token，避免总结请求也超窗。

模板没有 `context_summarization` 时，不读取这些参数，也不创建总结模型。

> 阈值不是模型上下文窗口上限，而是提前压缩的保护线。后续可结合模型配置表增加不同模型的上下文窗口信息，再动态计算阈值。

## 7. 总结模型与 SSE 隔离

总结调用也会触发模型流，因此必须与主 Agent 的 SSE 输出隔离。

AgentAssembler 根据 `context_summarization.model_code` 通过 `AgentModelService` 创建独立总结模型，再派生带流式隔离标记的模型：

```python
summary_model = configured_summary_model.with_config(
    tags=["nostream"],
    metadata={"lc_source": "summarization"},
)
```

`AgentStreamEventParser` 增加过滤规则：当流式 metadata、tags，或消息自身的 `additional_kwargs.lc_source` 表明它属于 `summarization` / `nostream` 时，不生成 `reasoning_delta`、`model_delta`、`tool_call` 等前端事件。

> 官方中间件写回 Checkpointer 的摘要是带 `additional_kwargs={"lc_source": "summarization"}` 的内部 HumanMessage，因此必须同时做消息级过滤；只检查流式 metadata 不够。

用户只看到主 Agent 的正常执行流，不会看到“总结历史消息”的内部内容。

### 7.1 SSE 状态事件

总结本身不向前端输出任何摘要正文或模型 Token，但需要通过 SSE 告知用户当前正在进行上下文压缩，避免长时间无反馈。

现有 Agent 流式执行已经消费 LangGraph 的 `custom` 流，因此总结中间件使用 `get_stream_writer()` 写入以下事件：

```json
{
  "type": "context_summary_started",
  "data": {
    "run_id": "当前运行 ID"
  }
}
```

```json
{
  "type": "context_summary_completed",
  "data": {
    "run_id": "当前运行 ID"
  }
}
```

总结失败时发送：

```json
{
  "type": "context_summary_failed",
  "data": {
    "run_id": "当前运行 ID",
    "message": "上下文总结失败，本轮将继续使用原始上下文。"
  }
}
```

前端交互规则：

1. 收到 `context_summary_started`：展示“正在总结会话上下文”。
2. 收到 `context_summary_completed`：将该状态更新为“会话上下文总结完成”。
3. 收到 `context_summary_failed`：展示轻量失败提示；主 Agent 仍会继续执行，前端不能将其视为整个运行失败。
4. 不展示摘要文本、Token、思考过程或原始历史消息，摘要仅属于内部工作记忆。

## 8. 总结 Prompt

使用平台中文 Prompt，要求摘要聚焦对后续对话真正有价值的信息：

```text
你负责压缩 Agent 的早期会话上下文。

保留：
1. 用户目标、偏好、限制条件和已确认决定。
2. 已完成任务、关键结论、重要数据和生成的产物。
3. 尚未完成的任务、失败原因、待用户确认事项。
4. 工具调用得到的、后续仍需依赖的关键事实。

不要保留：
1. 无关寒暄和重复表述。
2. 已失效的中间推理细节。
3. 可以从当前近期消息直接获得的重复内容。

仅输出结构化上下文摘要，不要向用户说话。
```

官方中间件会把此前摘要消息也纳入待总结范围，因此不需要单独维护 `summary_text` 字段。

## 9. 失败降级

LangChain 官方实现会将总结异常文本写进摘要结果。平台实现需要覆盖这一行为：

```text
总结模型调用异常
    -> 记录 error 日志和 run_id/thread_id
    -> 返回 None
    -> 不修改 state.messages
    -> 主 Agent 按原始上下文继续执行
```

总结失败不能导致主 Agent 失败，也不能把异常内容伪装成正常会话摘要。

## 10. 与现有中间件的顺序

建议中间件装配顺序：

```text
基础工具中间件
    -> InterruptMiddleware
    -> PlanningMiddleware（可选）
    -> ConversationSummarizationMiddleware（模板配置且有 conversation_id 时）
    -> FileContextMiddleware
    -> InjectRetrievalContextMiddleware
    -> A2AAgentContextMiddleware
```

总结中间件处理 Checkpointer 中已有的 `messages`；附件、检索、A2A、规划等动态上下文继续由各自中间件在模型调用前注入，不应被误写入历史摘要。

## 11. 与附件和规划能力的关系

### 附件

附件正文不直接写入 `messages`，只注入文件索引并通过工具按需读取。因此总结中间件不处理附件全文，也不会替代附件检索工具。

### 规划

任务计划存储在 LangGraph State 的 `task_plan` 字段中，不能仅依赖摘要保留。PlanningMiddleware 仍应在每次模型调用前根据当前 `task_plan` 注入执行规则和计划状态。

### 中断恢复

中断恢复必须使用原 `conversation_id` 对应的 `thread_id`。恢复后若达到阈值，可正常执行总结；`interrupt_payload`、`resume_value` 等状态字段不能由总结中间件修改。

## 12. 实施步骤

1. 新建 `middlewares/conversation_summarization_middleware.py`，继承官方中间件。
2. 添加平台中文总结 Prompt、`nostream` 标记和失败降级逻辑。
3. 在 `MiddlewareFactory` 中默认装配该中间件。
4. 在 `AgentStreamEventParser` 中过滤总结模型事件。
5. 增加 `summary_started`、`summary_succeeded`、`summary_skipped`、`summary_failed` 日志。
6. 进行长会话、工具调用配对、中断恢复、规划状态、流式输出回归测试。

## 13. 验收标准

1. 模板未配置 `context_summarization` 时，不创建总结模型、不装配总结中间件。
2. 无 `conversation_id` 的一次性任务或 A2A 子 Agent 不装配总结中间件。
3. 短会话未达到阈值时，不产生额外总结模型调用。
4. 长会话达到阈值后，Checkpointer 最新 `messages` 变为摘要消息加近期消息。
5. `agent_messages` 中的用户问题和最终回复没有被删除或修改。
6. 前端 SSE 不展示总结模型的任何 Token 或思考内容。
7. 工具调用请求与对应 ToolMessage 不会被拆开。
8. 总结模型失败时，主 Agent 仍可继续运行，且 Checkpointer 消息不被清空。
9. 总结开始和完成时，前端分别收到 `context_summary_started`、`context_summary_completed`，且不包含摘要正文。
10. 规划任务、中断恢复和附件读取在总结后仍可正常工作。

## 14. 非目标

- 第一版不把摘要写入长期记忆。
- 第一版不提供前端手动“立即总结”按钮。
- 第一版不做历史消息全文检索工具。
- 平台通过 `.env` 提供默认总结阈值；确有差异化需求时，Agent 模板可以显式覆盖。

后续如果 Agent 需要准确回查很久以前的原始会话内容，可基于 `agent_messages` 按 `conversation_id` 实现独立历史消息检索工具，而不是把全部历史重新塞回 Checkpointer。

## 环境变量配置

平台通过 AI-backend 的 `.env` 提供会话总结默认阈值：

```env
AGENT_CONTEXT_SUMMARY_TRIGGER_TOKENS=12000
AGENT_CONTEXT_SUMMARY_KEEP_MESSAGES=20
AGENT_CONTEXT_SUMMARY_TRIM_TOKENS=4000
```

配置优先级为：Agent 模板 `context_summarization` 中明确填写的值高于 `.env` 默认值。
模板只配置 `model_code` 并省略阈值时，使用 `.env`；修改 `.env` 后需要重启 AI-backend。

另外，Agent 图运行保护参数也由 `.env` 统一管理：

```env
AGENT_RECURSION_LIMIT=50
AGENT_TOOL_ERROR_MAX_LENGTH=500
```
